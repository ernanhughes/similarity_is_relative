## Frozen scaling

Fit the robust scaler on true training primitives only:

```text
scaled = (value - training median) / max(training IQR, 1.0)
```

Apply the resulting median and scale to both training candidates and test queries. Record the values and logical array hashes in the manifest report.

## Token-length deciles

The candidate token-length deciles are frozen as follows:

1. compute eleven quantile boundaries from selected training token counts;
2. use NumPy's `linear` quantile method;
3. assign both training candidates and test queries with `searchsorted(..., side="right")` against the nine internal boundaries;
4. use the candidate-derived boundaries for every query;
5. record the boundaries and their logical array hash.

Repeated boundaries can produce empty deciles. A query mapped to an empty candidate decile remains represented and has zero informative pairs.

## Oracle ordering

For each test query:

1. select every training candidate in the query's token-length decile;
2. compute Chebyshev distance over robust-scaled true primitives;
3. sort by ascending oracle distance;
4. break equal-distance ordering ties by ascending candidate stable key.

The stable-key tie break only makes the candidate order deterministic. Candidate pairs with equal oracle distances are still excluded.

## Eligible pairs

For each ordered candidate list:

- the closer candidate precedes the farther candidate;
- rank separation must be between 5 and 25 positions, inclusive;
- oracle-distance ties are excluded;
- every remaining pair is eligible before the per-query cap.

Every pair records:

- query index and stable key;
- closer and farther candidate indices and stable keys;
- closer and farther oracle distances;
- closer and farther oracle ranks;
- rank separation;
- deterministic selection SHA-256;
- final pair order after selection.

## Deterministic pair selection

The selection digest is:

```text
SHA256(
    manifest_seed + "\n" +
    query_stable_key + "\n" +
    closer_candidate_stable_key + "\n" +
    farther_candidate_stable_key
)
```

The manifest seed remains:

```text
8112026
```

Select the first 128 eligible pairs in ascending digest order. Stable keys are used instead of mutable row positions so the selection identity remains attached to canonical rows.

## Sparse and zero-pair queries

The complete manifest uses two JSONL files:

```text
option-b-hard-negative-queries-v1.jsonl
option-b-hard-negative-pairs-v1.jsonl
```

The query file contains exactly one row for every selected test query in canonical order.

A query is flagged `sparse` when it has fewer than 32 eligible pairs before the 128-pair cap. Sparse queries retain every eligible pair.

A query with zero eligible pairs:

- remains in the query file;
- is flagged `zero_informative_pairs`;
- contributes no hard-negative triplets later;
- may not be silently removed from retrieval metrics.

The report fails if its query row count differs from the selected test row count.
